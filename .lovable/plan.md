

# Comprehensive Security & Quality Remediation Plan

This plan addresses all 56 issues from the audit. Issues are grouped into implementable phases matching the suggested execution order.

---

## Phase 1: Security Containment (Issues 1-5)

### Issue 1: Remove committed credentials
**Verified**: `.mcp.json` contains Supabase PAT and Exa API key. `.env` has anon key. `client.ts` hardcodes anon key. Migration `20260226203309` embeds bearer token in SQL.
- Remove `.mcp.json` from tracked files (add to `.gitignore`)
- Create `.env.example` with placeholder values
- Note: The anon/publishable key in `client.ts` is auto-generated by Lovable and is public by design -- this is expected. The PAT in `.mcp.json` and the bearer token in the migration are the real concerns.
- Document Git history cleanup steps in README

### Issue 2: Move secrets to Supabase secrets
**Verified**: Edge functions already use `Deno.env.get()` for `SUPABASE_SERVICE_ROLE_KEY`, `OPENAI_API_KEY`, etc. Secrets are already configured in Supabase. The Settings UI exposes `api_key` and `bot_token` fields in the browser -- this is the real problem (addressed in Issue 9).
- Confirm all functions use env-based secrets (already done)
- Remove secret fields from browser-editable settings (Issue 9)

### Issue 3: Lock down privileged edge functions
**Verified**: `config.toml` is missing `media-processor` and `media-cleanup` declarations. `worker` and `db-cleanup` have `verify_jwt = false`.
- Add all functions to `config.toml`
- Set `verify_jwt = false` for all (per Lovable's signing-keys approach) and validate JWT in code instead

### Issue 4: Add in-function authorization
**Verified**: No edge function checks user identity or role. `admin-retry` accepts any request with the anon key.
- Create shared auth helper using `getClaims()` pattern
- Add auth checks to `admin-retry`, `worker` (service-only), `media-processor`, `media-cleanup`, `db-cleanup`
- Internal functions validate `x-internal-token` header
- Browser-facing functions validate admin role

### Issue 5: Replace hardcoded cron bearer token
**Verified**: Migration `20260226203309` embeds the full anon key in SQL for the cron job.
- Create new migration to update the cron job to use `current_setting('app.settings.service_role_key')` or call via `supabase.functions.invoke` internally
- Alternative: have cron call a DB function that invokes cleanup directly

## Phase 2: Authorization & Data Access (Issues 6-9)

### Issue 6: Implement admin RBAC
**Verified**: `AuthContext.tsx` has no role concept. `AppLayout.tsx` only checks `user` existence.
- Create `user_roles` table with `app_role` enum (`admin`, `viewer`)
- Create `has_role()` security definer function
- Add role loading to `AuthContext`
- Add `RequireAdmin` route guard component

### Issue 7: Rewrite RLS policies
**Verified**: All tables use `auth.uid() IS NOT NULL` which allows any authenticated user full access.
- Replace all `FOR ALL` policies with role-based policies using `has_role()`
- Admin gets full access; viewer gets SELECT only on appropriate tables
- Service role bypasses RLS for edge functions

### Issue 8: Remove direct browser writes to operational tables
**Verified**: `Settings.tsx` does `supabase.from('settings').upsert()`. `Monitoring.tsx` does `supabase.from('posts').update()` and `supabase.from('jobs').insert()`. `Threads.tsx` does `supabase.from('deliveries').insert()`.
- Create edge function `admin-actions` with endpoints for: save settings, edit translation, retry step, reprocess, post thread
- Replace all browser `.insert()`/`.update()` calls with `supabase.functions.invoke()`

### Issue 9: Split privileged settings from browser
**Verified**: Settings UI exposes `api_key` (OpenAI) and `bot_token` (Telegram) as editable text fields.
- Remove secret fields from the OpenAI and Telegram settings tabs
- Keep only non-secret config: model, temperature, prompts, parse_mode, template
- Secrets stay in Supabase function secrets only

## Phase 5: Queue & Pipeline Reliability (Issues 17-23)

### Issue 17: Transactional job claiming
**Verified**: Worker does `select` then `update` separately -- race condition possible.
- Create `claim_jobs(batch_size)` RPC with `FOR UPDATE SKIP LOCKED`

### Issue 18: Durable queue fields
- Add `locked_at`, `locked_by`, `lease_expires_at`, `idempotency_key` columns to `jobs`
- Add composite indexes

### Issue 19: Idempotency enforcement
- Generate deterministic keys like `translate:<tweet_id>`
- Use upsert/conflict handling on insert

### Issue 20: Dead-letter queue
- Create `dead_letter_jobs` table
- Move permanently failed jobs there after max attempts

### Issue 21: Standardize retry policy
- Centralize retry rules per job type in worker
- Honor Telegram `retry_after`, use exponential backoff for others

### Issue 22: Reconciliation jobs
- Create periodic RPC to detect orphaned/stuck jobs
- Auto-recover common partial failures

### Issue 23: Safe dry-run cleanup
- Add `dry_run` parameter to `db-cleanup` and `media-processor`
- Return counts without deleting
